Worker 是什么，绑核后条数谁说了算

SwiftShader / marl · 面向 4 核绑核容器

Worker 是 SwiftShader 雇来在 CPU 上画像素的线程，不是核，也不是绑核配额。

Worker 条数 = ThreadCount（ini 里写了且大于 0）
否则 = min(这个进程看见的逻辑核数, 16)

绑核只可能改变「看见的逻辑核数」。它不直接等于 Worker 条数。

1. Worker 是什么

SwiftShader 没有 GPU。一帧要画的三角形、像素被切成很多小任务，丢进 marl 队列。Worker 就是排队领任务的那几条专用线程，perf 里名字一般是 Thread<00>、Thread<01>…

一条 Worker 领到活之后，顺序做：顶点着色 → 三角形装配 → 片元着色 / 纹理采样 → 写颜色。没有「采样专用线程」和「着色专用线程」，都是同类劳动力。

不是这些东西
  • 不是 CPU 核，也不是 cpuset 划给你的那几颗核
  • 不是应用的 RenderThread（那条线程负责提交 Vulkan 命令）
  • 不是 surfaceflinger 主线程

2. 绑核管什么，不管什么

把核想成椅子，Worker 想成雇来的人：

4 核绑核 = 4 把椅子（这个容器只允许坐这 4 把）

核 0 核 1 核 2 核 3

ThreadCount=2 = 雇 2 个人。人可以坐任意空椅子，但同时最多占 2 把。

Worker 0 Worker 1 空着 空着

另外 2 把椅子不是划给别人的财产，只是你这边没人去坐。SF 和应用的 Worker 都抢同一套 4 把椅子（共用 cpuset）。

绑核 / cpusetWorker / ThreadCount
管什么允许在哪些核上跑这个进程雇几条渲染线程
4C 容器典型值4 个核，SF 和应用共用ini 写几条就是几条
会不会自动变成 4—只有「没写 ThreadCount，且进程看见的核真是 4」时才会

3. 绑核之后，条数到底由谁定义

源码就这一句（SwiftConfig.cpp）：

threadCount = (ini.ThreadCount == 0)
            ? min(sysconf(_SC_NPROCESSORS_ONLN), 16)
            : ini.ThreadCount;

按顺序看：

  1. 进程 cwd 里有 SwiftShader.ini，且 [Processor] ThreadCount 大于 0 → 就是这个数，和绑了几个核无关。
  2. 否则（没有 ini，或 ThreadCount=0）→ min(nproc, 16)。nproc 来自 sysconf(_SC_NPROCESSORS_ONLN)，是这个进程看见的在线 CPU。
  3. 绑核如果让进程真的只看见 4 个核，默认就是 min(4, 16) = 4。
  4. 绑核如果没让 nproc 变小（只设了 --cpus=4 配额、或进程启动时还看见整机很多核）→ 默认仍是 min(大数, 16) = 16。

redroid 是 Android，marl 不会按 AffinityPolicy=one 把 Worker 钉到某一颗核。绑核靠的是容器 cpuset，不是 ini 里的亲和性。

4. 还要乘「几份 ICD」

应用和 surfaceflinger 各加载一份 SwiftShader，各有一份调度器，各读自己 cwd 的 ini。绑的是同一组 4 核。

  • 两边都默认、且 nproc=4 → 4 + 4 = 8 条 Worker 抢 4 把椅子
  • 两边 ini 都写 2 → 2 + 2 = 4 条
  • 游戏：应用 4、SF 1 → 5 条，应用可以把 4 核占满

核对：nproc、CpusetCpus、两个 pid 的 ls -l /proc/<pid>/cwd/SwiftShader.ini，以及各有几条 Thread<NN>。

5. 一句话

绑核决定能坐哪几把椅子。Worker 条数决定雇了几个人。人少椅子多，核会空；人多椅子少，就挤、还容易空转。条数只认 ini 的 ThreadCount，否则认 min(看见的核, 16)，不认「我绑了 4 核所以一定是 4 条」。

对应源码：src/System/SwiftConfig.cpp 的 getSchedulerConfiguration()， third_party/marl/src/thread.cpp 的 numLogicalCPUs()。 中文调度说明见 scheduler.zh.md。
